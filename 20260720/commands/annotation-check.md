# 注释审查命令

**触发时机**：每次修改业务代码前必须执行

## 执行流程

### 1. 输出检查清单

```
【X档 · 编辑前检查】
- [ ] 已读取目标代码，理解业务上下文
- [ ] 已确认修改范围，不扩大影响
- [ ] 已确认版本控制纪律
- [ ] 涉及业务注释时，按 annotation.md 标准审查
- [ ] 涉及前端 **.vue、**.html、**.js、**.css 文件修改时，按 frontend.md 标准审查
→ 全部基于事实勾选后方可编辑
```

### 2. 审查全方法业务逻辑段落

**必须审查该方法的全部业务逻辑段落**，不能只关注修改的部分。

### 3. 按照注释内容维度覆盖

1. **业务目的**：这段代码解决什么需求或防止什么业务错误？
2. **数据流转**：数据从哪来，经过什么转换，写到哪里或返回给谁？
3. **外部交互**：调用什么系统，目的、数据格式和失败策略是什么？
4. **持久层调用**：查询/写入什么数据，条件含义、返回值和后续用途是什么？
5. **分支场景**：什么业务场景进入该路径，结果有什么差异？
6. **风险约束**：为什么要保留顺序、去重、恢复字段、隐藏金额或避免 N+1？

### 4. 数据库调用必须说明6个要素

1. 数据来源：业务实体或表名、关键字段
2. 业务目的：为什么需要这次查询
3. 条件含义：ID、状态、组织、项目编码等条件代表什么
4. 结果用途：查询结果用于哪个 Map、分支、响应字段或后续调用
5. 空结果处理：跳过、返回空、报错还是降级
6. 性能意图：处于循环相关逻辑时，说明批量查询如何替代逐条访问

### 5. 执行编辑后复查（DoD）

```
【编辑后复查】
- [ ] 方法全覆盖：所有适用逻辑段落均已审查
- [ ] 查询用途：每个数据库调用都有来源、目的、条件、结果去向
- [ ] 分支语义：关键分支说明业务场景和影响
- [ ] 一致性：注释与当前代码完全一致
- [ ] 变更范围：未为注释或分层扩大历史代码重构
- [ ] 代码实查：必须确认注释已写入文件，禁止在交付总结中声称已添加但实际未写入
→ 全部通过后，代码任务才算完成
```

## 强制要求

**未执行注释审查，禁止修改代码。**
