# Bug修复工作流

## 核心流程

```text
数据库验证（可选）→ 三步分析（追踪 → 诊断 → 修复）
→ 全方法注释复查 → 定向验证 → 相邻回归
```

---

## 三步分析协议（强制执行）

**禁止跳过追踪直接修复。** 每个 Bug 必须按以下顺序处理：

### 第 1 步：追踪（Trace）

- 用 Grep/Read 映射完整数据流（前端 → Controller → Service → Mapper/SQL）
- 涉及导出 Bug 时：grep 前端导出按钮的 axios URL，追踪到确切的后端方法（**不是列表查询方法**）
- 涉及显示 Bug 时：确认 API 实际返回的是编码还是标签（用数据库查询验证，不假设）
- **输出**：简要数据链路摘要，标注可能的断裂点

### 第 2 步：诊断（Diagnose）

- 确定精确的断裂点，用代码片段或数据对比作为证据
- 有多个候选根因时，逐个排除并记录
- **输出**：根因 + 证据

### 第 3 步：修复（Fix）

- 应用最小定向变更
- **编辑前验证文件路径**（Grep/Glob 确认，不假设）
- 修复后检查无副作用

---

## 数据库排查（第 0 步）

> 当数据状态不确定时，在代码分析前先查数据库。

### 连接方式

- 读取项目主配置文件（`hussar-web/src/main/resources/application.yml`）获取 `spring.profiles.active`，再从对应环境配置读取数据源信息
- 若连接信息不可用或连接失败，**询问用户**获取数据库地址
- **禁止**在代码或日志中输出完整密码

### 使用场景

| 场景 | SQL 示例 |
|------|----------|
| 字段显示异常 | `SELECT field_name, dict_code FROM table WHERE id = ?` |
| 导出数据不一致 | 对比导出 SQL 与列表 SQL 结果集 |
| 字典翻译缺失 | `SELECT * FROM sys_dict WHERE dict_type = 'xxx'` |
| 关联数据为空 | `SELECT * FROM ref_table WHERE foreign_key = ?` |
| 状态流转异常 | 查状态字段当前值 |

### 排查原则

1. **先查数据再改代码**：不确定数据状态时，先 SELECT 确认
2. **验证假设**：对数据流的假设用 SQL 验证后再修复
3. **保留证据**：查询结果作为排查报告的一部分

---

## 各阶段处理

| 步骤 | 条件 | 处理 |
|------|------|------|
| 复现 | 无法稳定复现 | 先收集日志、请求与数据条件，不猜测 |
| 定位 | 跨多个模块 | 并行只读搜索，主代理汇总链路 |
| 根因 | 有多个候选 | 逐个排除并记录证据 |
| 修复 | 涉及核心业务语义 | **按 `business-assumptions.md` 执行业务假设门控**，先确认影响范围 |
| 注释 | 修改任意方法 | 按 `annotation.md` 审查全部逻辑段落 |
| 验证 | 见下方「验证流程」 | 按场景选择验证方式 |
| 回归 | 影响权限、状态、金额 | 验证相邻场景和反向分支 |

## 专项排查流程

### 导出 Bug 专项

> 详细排查流程见独立 skill `/fix-export`。以下为快速摘要。

高频根因：导出方法与列表查询方法是独立代码路径，导出方法缺少条件清理或字段映射。

1. grep 前端导出按钮的 axios URL（**不是**列表查询 URL）
2. 追踪该 URL → Controller → Service → Mapper，找到确切的导出后端方法
3. **数据库验证**：用 mysql 执行导出 SQL，对比列表查询 SQL 结果
4. 对比导出方法与列表查询方法的差异（条件清理、字段映射、过滤逻辑）
5. 仅对导出方法做最小 diff
6. **禁止假设**页面查询方法就是导出方法

### 字典显示 Bug 专项

> 高频根因：假设 API 返回编码并修改数据层，实际 API 已返回标签或表格可编辑。

1. **数据库验证**：查数据表实际存储值（编码 or 标签）
2. **API 验证**：用 Chrome DevTools 检查接口实际响应格式
3. 判断表格是否可编辑：
   - 可编辑 → 仅在展示层修复（template formatter/slot）
   - 不可编辑 → 可在数据层或展示层修复
4. 检查字典表映射是否存在

### 文件路径验证

编辑前**必须执行**：
1. Grep 目标函数名或关键字，确认文件路径
2. Glob 同名文件，列出候选路径
3. 编辑前输出：「将编辑 [完整路径]，因为 [与当前 Bug 的关联]」

## 验证流程

### 前端 Bug 验证

> **浏览器工具以 CLAUDE.md §五 为硬规则**：一律使用 `mcp__chrome-devtools__` 系列。
> 服务已运行时直接连接，**禁止重复启动**。
> **布局修复以 `frontend.md`「DOM 结构优先于 CSS 补丁」为硬规则**：先读 DOM 结构，再选方案，禁止盲改 CSS。

1. `mcp__chrome-devtools__list_pages` 检查已有页面
2. `mcp__chrome-devtools__select_page` 选择目标页面
3. `mcp__chrome-devtools__take_snapshot` 获取页面结构
4. 执行交互操作（`click` / `fill` / `press_key`）
5. `mcp__chrome-devtools__take_screenshot` 截图对比
6. `mcp__chrome-devtools__list_console_messages` 检查控制台错误
7. 将截图/日志/网络响应作为验证证据

### 后端 Bug 验证

1. 提供 curl 命令或接口测试步骤
2. 说明预期返回值和实际返回值差异
3. 涉及数据库变更时，**用 mysql CLI 查询验证**（读取 application.yml 获取连接信息）
4. 无法自动验证时，说明阻断原因和手动验证步骤

### 阻断升级机制

| 修复次数 | 处理 |
|----------|------|
| 第 1 次失败 | 重新分析根因，记录失败原因 |
| 第 2 次失败 | 停止修复，列出候选根因和排除证据，向用户确认方向 |
| 第 3 次失败 | 标记为复杂问题，建议用户介入或提供更多上下文 |

## 常见陷阱

- 复现时不要猜测，要收集实际日志
- 修复时不要顺手重构
- 验证时不要声称已完成
- 回归时不要遗漏反向分支
- 导出 Bug 不要假设导出方法与查询方法相同
- 显示 Bug 不要假设 API 返回格式，先验证

---

## 交付要求

- 根因或需求实现说明
- 修改文件和业务影响
- 验证命令、结果或环境阻断
- 未处理风险
- 一条业务注释示例
