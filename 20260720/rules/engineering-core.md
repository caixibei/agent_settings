# 工程核心规范

> 决策优先级见 CLAUDE.md §二，不在本文件重复。
> 设计模式与组件化决策见 design-principles.md。
> 历史代码修改流程见 workflows.md。

## 安全编码

- SQL注入：禁止拼接用户输入，使用 MyBatis `#{}` 或参数化查询
- 输入校验：在系统边界校验长度、类型、范围和白名单
- 权限校验：删除、状态、金额和权限变更前验证当前用户权限
- 敏感信息：密码、密钥、token、连接串不得硬编码或写日志
- 文件上传：校验MIME、扩展名和大小，存入非Web直访路径
- 输出安全：用户可控内容进入HTML前防XSS

## 持久层与事务

- 新增事务只放Service；历史位置不因本次局部修复强制迁移
- 事务边界与完整业务操作一致，避免半成功状态
- checked exception需要回滚时显式指定 `rollbackFor = Exception.class`
- 避免在事务内发邮件、调第三方API或执行长耗时操作
- 批量操作评估SQL长度、分批策略、索引和一致性
- 生成`IN`前短路，禁止空集合进入MyBatis `<foreach>`

## 查询与性能

- 循环内出现getById/list/selectOne/远程调用时，先判断N+1
- 可批量时先收集主键或业务键，一次查询并按ID转Map
- 批量查询必须返回用于结果归属的主键
- 全量处理后内存分页属于明确风险；能安全修改时改为数据库分页
- 性能优化不得改变权限范围、过滤规则、排序口径和总数含义

## 调试前置：Touchpoint 地图

修复数据展示/换算类 Bug（单位转换、字段映射、字典翻译等）时，**动手前先画出该字段在全代码库的读写触达点地图**，确认覆盖链完整后再统一修复。逐点打补丁（修一处不查其余触达点）是此类 Bug 反复返工的首要原因。

1. **列出触达点**：前端赋值 → 前端展示 → 前端回显覆盖（editTable_XXReplaceData 系列）→ 后端 Service 装配 → Mapper XML/MyBatis → 字典/低码配置
2. **标出覆盖链**：标记哪些触达点可能**静默覆盖**其他触达点的值（编辑回显覆盖前端修正、copyProperties 覆盖上下文字段）
3. **统一修复**：在所有触达点一次性修复；修复后验证「新增表单」和「列表展示」两个视图均正常

## 调试前置：数据库连接

排查数据问题或梳理业务表结构时，**主动连接数据库验证**，不要仅依赖代码静态分析。

### 连接方式

1. 读取项目主配置文件（如 `application.yml`），找到 `spring.profiles.active` 的值
2. 读取对应的环境配置文件（如 `application-{profile}.yml`）
3. 从数据源配置节点（如 `spring.datasource.dynamic.datasource.master`）获取 `url`、`username`、`password`

> 具体文件路径因项目而异，首次使用时结合项目结构确认。禁止在代码或记忆文件中硬编码连接信息。

### 使用场景

| 场景 | 操作 |
|------|------|
| 字段显示异常（编码 vs 标签） | `SELECT * FROM table WHERE id = ?` 查看实际存储值 |
| 导出数据不一致 | 对比导出 SQL 与列表查询 SQL 的结果集 |
| 字典翻译缺失 | 查字典表确认 code → label 映射是否存在 |
| 关联数据为空 | 查外键表确认关联记录是否存在 |
| 状态流转异常 | 查状态字段当前值和历史变更 |

### 排查原则

1. **先查数据再改代码**：不确定数据状态时，先 SELECT 确认
2. **验证假设**：对数据流的任何假设，用 SQL 验证后再应用修复
3. **保留证据**：将查询结果作为排查报告的一部分记录

## 渐进式架构治理

目标结构：请求 → Controller → Service → Mapper/DAO → DB

**新增代码**：严格遵循分层，跨模块新增调用优先走目标模块Service。优先采用设计模式（策略/工厂/模板方法等）降低复杂度，参见 design-principles.md。

**历史代码**：
- Controller已承载业务逻辑时，允许原位最小修复
- 不因历史分层问题强制重构
- 原位修复必须补足业务注释

## 导出方法匹配

导出功能的后端方法通常是**独立代码路径**，与页面列表查询方法分开编写。

修复导出 Bug 时的排查步骤：
1. grep 前端导出按钮的 axios URL（**不是**列表查询 URL）
2. 追踪到确切的后端 Controller 方法
3. 对比导出方法与列表查询方法的差异（条件清理、字段映射、过滤逻辑）
4. 仅对导出方法做最小 diff，不修改列表查询方法

**禁止**假设页面查询方法就是导出方法。

## 文件路径验证（强制门控）

编辑前**必须**通过 Grep 或 Glob 确认文件完整路径。项目中有多个同名文件在不同模块目录，路径混淆会导致改错文件。

**执行步骤（缺一不可）**：
1. Grep 目标函数名或关键字，获取候选文件列表
2. 若存在多个同名文件 → Glob 确认所有候选路径
3. **【强制输出】** 编辑前必须明确输出：「将编辑 [完整路径]，因为 [与当前 Bug 的关联]」
4. 确认路径后方可调用 Edit/Write

**高风险区域**：同名 Entity 跨模块（如 BpCommissionSheet 5 个版本）、同名 Vue 文件（多个 crkls.vue）、导出方法与查询方法在不同 Controller。

> 详细的同名文件检查清单见 `business-assumptions.md`「文件路径验证门控」。

**禁止行为**：
- ❌ 假设文件路径直接编辑（不 Grep 验证）
- ❌ 仅凭类名定位文件，不确认包路径
- ❌ 跳过同名文件检查直接选择第一个结果

## 需要用户确认的情况

- 拆分超长核心方法
- 改变事务边界
- 将Controller逻辑迁移到Service
- 跨模块改接口
- 修改工作流、权限或金额计算

## 完成检查

### 后端

- 业务结果和边界场景符合预期
- 权限、状态、金额和敏感数据未受损
- 查询无明显新增N+1
- 历史分层问题未导致无关重构
- 业务注释符合annotation.md
- 已执行可用验证，或明确说明环境阻断

### 前端布局

- 查询条件在最小适用宽度（1280px）下全部可见，无字段被挤出视口
- 表格高度随查询区换行自动调整，不会被挤出视口底部
- 空间不足时内容换行而非溢出隐藏（禁用 `overflow: hidden` 隐藏业务内容）
- 布局修改优先调整容器结构，其次流式布局，最后 CSS 计算
- 已在浏览器验证或说明环境阻断原因
