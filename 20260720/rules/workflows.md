# 开发工作流

> 决策优先级见 CLAUDE.md §二。
> 工程规范（安全编码、持久层、性能）见 engineering-core.md。
> 设计模式与组件化见 design-principles.md。
> 业务注释标准见 annotation.md。
> 陷阱参考见 pitfalls.md。

## 核心原则

- 一次只解决已确认的问题
- 历史代码默认最小修复，不顺手做架构重构
- 新增代码优先采用设计模式和组件化
- 修改方法后必须执行全方法业务注释复查
- 无验证证据时不得声明完成

## 流程路由

| 场景 | 详细 Skill | 说明 |
|------|-----------|------|
| Bug 修复 | `/bug-fix` | 复现 → 定位 → 根因 → 最小修复 → 注释复查 → 验证 |
| 新增功能 | `/feature-dev` | 需求理解 → 影响分析 → 接口设计 → 实现 → 注释 → 测试 |
| 代码审查 | `/code-review` | 按严重级别分类，逐维度审查 |
| 交付 | `/delivery` | 标准交付结构模板 |

## 通用流程摘要

### Bug 修复

```text
复现确认 → UI/接口/Service/SQL 链路定位 → 根因分析
→ 最小修复 → 全方法注释复查 → 定向验证 → 相邻回归
```

### 新增功能

```text
需求理解 → 表/接口/权限/状态影响分析 → 接口设计
→ Service 业务实现 → Mapper/SQL → 前端 → 注释复查 → 测试
```

### 性能优化

```text
复现 → 计时 → 定位 → 单根因优化 → 验证
```

### 重构

```text
目标 → 评估 → 小步修改 → 行为回归
```

## 历史代码修改

允许原位修复的场景：
- Controller 已存在业务逻辑
- 方法较长但当前问题边界明确
- 直接调 Mapper 是既有模式
- 拆分会改变事务、流程上下文或扩大测试范围

处理要求：
1. 保持现有业务结果
2. 控制在最小文件和方法范围
3. 补齐完整业务注释
4. 记录未处理架构风险
5. 不把历史分层问题作为当前任务失败条件

## 交付要求

> 详细模板见 `/delivery` skill。

交付必须包含：
- 根因或需求实现说明
- 修改文件和业务影响
- 验证命令、结果或环境阻断
- 未处理风险
- 一条本次业务注释示例
