# 业务注释要求（绝对强制）

适用于代码新增、修改、删除和重构。目标是保存难以从语法直接推断的业务知识，降低历史代码维护风险。

**触发时机**：每次 Edit/Write 修改业务代码前自动执行，与代码变更在同一次 Edit 中一起写入。

## 核心原则

- 注释解释”为什么存在、数据从哪来、处理后到哪里去”，**不翻译代码**。
- 修改方法任意一行，必须审查该方法全部业务逻辑段落。
- 业务正确性优先。历史方法复杂时，不为满足注释或分层要求强制拆分。
- 无法确认业务意图时标记 `// TODO: [待确认业务意图]` 并提示用户，不得猜测。
- 清单必须基于已读取代码，**禁止先勾选后补审查**。

## 严格执行流程（必须遵守）

### 编辑前：输出检查清单

每次 Edit/Write 修改业务代码时，**必须先输出以下检查清单**：

```
【X档 · 编辑前检查】
- [ ] 已读取目标代码，理解业务上下文
- [ ] 已确认修改范围，不扩大影响
- [ ] 已确认版本控制纪律
- [ ] 涉及业务注释时，按 annotation.md 标准审查
- [ ] 涉及前端 **.vue、**.html、**.js、**.css 文件修改时，按 frontend.md 标准审查
→ 全部基于事实勾选后方可编辑
```

### 编辑时：审查全方法业务逻辑段落

**必须审查该方法的全部业务逻辑段落**，不能只关注修改的部分。每个逻辑段落都需要：
1. 识别其业务目的
2. 确认数据来源和去向
3. 添加符合规范的业务注释

**业务注释必须在同一次 Edit/Write 中与代码变更一起写入，禁止分两次编辑（先改代码再补注释）。**

### 编辑后：执行复查（DoD）

**必须执行编辑后复查**，确保：
1. 方法全覆盖：所有适用逻辑段落均已审查
2. 查询用途：每个数据库调用都有来源、目的、条件、结果去向
3. 分支语义：关键分支说明业务场景和影响
4. 一致性：注释与当前代码完全一致
5. 变更范围：未为注释或分层扩大历史代码重构
6. **代码实查：必须确认注释已写入文件，禁止在交付总结中声称已添加但实际未写入**

## 深入理解规范

### annotation.md 的核心目的

**保存难以从语法直接推断的业务知识**，降低历史代码维护风险。

这意味着：
- 注释不是为了描述代码做了什么（这是代码本身就能看出来的）
- 注释是为了解释**为什么这样做**、**数据从哪来**、**处理后到哪里去**
- 注释是为了让未来的维护者理解业务背景和设计意图

### 业务注释的核心要求

业务注释要解释三个核心问题：
1. **为什么存在**：解决什么需求或防止什么业务错误？
2. **数据从哪来**：数据来源、转换过程、最终去向
3. **处理后到哪里去**：返回给谁、写入哪个表、触发什么后续操作

### 数据库调用注释的6个要素

涉及 Mapper、DAO、getById、list、page、select*、MyBatis SQL 时，注释**必须说明**：

1. **数据来源**：业务实体或表名、关键字段
2. **业务目的**：为什么需要这次查询
3. **条件含义**：ID、状态、组织、项目编码等条件代表什么
4. **结果用途**：查询结果用于哪个 Map、分支、响应字段或后续调用
5. **空结果处理**：跳过、返回空、报错还是降级
6. **性能意图**：处于循环相关逻辑时，说明批量查询如何替代逐条访问

## 逻辑段落清单

以下每项在适用时都是独立逻辑段落：

1. 入参和登录上下文准备
2. 角色、组织、权限或数据范围判断
3. 查询条件构造
4. 每次 Mapper、Service 查询或外部系统调用
5. 查询结果转 Map/Set、聚合、去重和批量装配
6. 关键 if/switch/提前返回/continue 分支
7. 状态、流程节点、金额、敏感字段处理
8. BeanUtils.copyProperties 等可能覆盖业务字段的操作
9. 排序、分页、总数计算和响应构造
10. 异常、空结果、历史脏数据和降级处理

## 注释内容维度（至少覆盖两个）

| 维度 | 必须回答的问题 | 常见错误 |
|---|---|---|
| ① 业务目的 | 解决什么需求或防止什么业务错误？ | 只写”查询用户”，不写”为什么需要查询用户” |
| ② 数据流转 | 数据从哪来，经过什么转换，写到哪里或返回给谁？ | 只写”设置用户名”，不写”用户名从哪里来，用到哪里” |
| ③ 外部交互 | 调用什么系统，目的、数据格式和失败策略是什么？ | 只写”调用接口”，不写”调用什么接口，目的是什么” |
| ④ 持久层调用 | 查询/写入什么数据，条件含义、返回值和后续用途是什么？ | 只写”查询数据库”，不写”查询什么数据，条件是什么” |
| ⑤ 分支场景 | 什么业务场景进入该路径，结果有什么差异？ | 只写”如果条件成立”，不写”什么业务场景进入这个分支” |
| ⑥ 风险约束 | 为什么要保留顺序、去重、恢复字段、隐藏金额或避免 N+1？ | 只写”排序”，不写”为什么要排序，不排序会有什么问题” |

## 禁止行为（常见错误）

### ❌ 错误1：仅描述代码动作

**错误示例：**
```java
// 查询用户
User user = userMapper.selectById(userId);
// 设置用户名
user.setName(userName);
// 保存用户
userMapper.updateById(user);
```

**正确示例：**
```java
// 【用户信息校验】查询用户基本信息，用于验证用户是否存在及权限
// 数据来源：sys_user 表，根据用户ID查询
// 业务目的：确认用户存在且有操作权限
// 结果用途：后续判断用户角色和数据权限
User user = userMapper.selectById(userId);

// 【用户信息更新】更新用户姓名，记录最后修改时间
// 数据来源：前端传入的 userName 参数
// 业务目的：允许用户修改自己的显示名称
// 结果用途：更新 sys_user 表的 user_name 和 last_time 字段
user.setName(userName);
userMapper.updateById(user);
```

### ❌ 错误2：只注释修改行，忽略同方法其他段落

**错误示例：**
```java
public void updateUser(String userId, String userName) {
    // 查询用户
    User user = userMapper.selectById(userId);
    
    // 【新增】验证用户是否存在
    if (user == null) {
        throw new BusinessException("用户不存在");
    }
    
    // 更新用户
    user.setName(userName);
    userMapper.updateById(user);
}
```

**正确示例：**
```java
public void updateUser(String userId, String userName) {
    // 【用户信息查询】根据用户ID查询用户信息
    // 数据来源：sys_user 表
    // 业务目的：获取用户当前状态，用于后续校验和更新
    // 空结果处理：如果用户不存在，抛出业务异常
    User user = userMapper.selectById(userId);
    
    // 【用户存在性校验】验证用户是否存在
    // 业务目的：防止更新不存在的用户数据
    // 分支场景：用户不存在时抛出异常，阻止后续操作
    if (user == null) {
        throw new BusinessException("用户不存在");
    }
    
    // 【用户信息更新】更新用户姓名
    // 数据来源：前端传入的 userName 参数
    // 业务目的：允许用户修改自己的显示名称
    // 结果用途：更新 sys_user 表的 user_name 和 last_time 字段
    user.setName(userName);
    userMapper.updateById(user);
}
```

### ❌ 错误3：一条宽泛注释覆盖多个查询和分支

**错误示例：**
```java
// 处理用户信息
User user = userMapper.selectById(userId);
if (user != null) {
    user.setName(userName);
    userMapper.updateById(user);
    
    // 记录操作日志
    OperationLog log = new OperationLog();
    log.setUserId(userId);
    log.setOperation("更新用户信息");
    logMapper.insert(log);
}
```

**正确示例：**
```java
// 【用户信息查询】根据用户ID查询用户信息
// 数据来源：sys_user 表
// 业务目的：获取用户当前状态，用于后续校验和更新
User user = userMapper.selectById(userId);

if (user != null) {
    // 【用户信息更新】更新用户姓名
    // 数据来源：前端传入的 userName 参数
    // 业务目的：允许用户修改自己的显示名称
    user.setName(userName);
    userMapper.updateById(user);
    
    // 【操作日志记录】记录用户信息更新操作
    // 数据来源：当前操作用户ID和操作内容
    // 业务目的：审计追踪，记录用户操作历史
    // 结果用途：插入 operation_log 表
    OperationLog log = new OperationLog();
    log.setUserId(userId);
    log.setOperation("更新用户信息");
    logMapper.insert(log);
}
```

### ❌ 错误4：注释与代码行为不一致

**错误示例：**
```java
// 【用户权限校验】检查用户是否有管理员权限
// 业务目的：防止普通用户执行管理员操作
if (user.getRole() != null && user.getRole().equals("ADMIN")) {
    // 实际代码检查的是用户是否被禁用，而不是是否有管理员权限
    if (user.getStatus().equals("DISABLED")) {
        throw new BusinessException("用户已被禁用");
    }
}
```

**正确示例：**
```java
// 【用户状态校验】检查用户是否被禁用
// 业务目的：防止已禁用用户执行任何操作
// 分支场景：用户被禁用时抛出异常，阻止后续操作
if (user.getStatus().equals("DISABLED")) {
    throw new BusinessException("用户已被禁用");
}
```

### ❌ 错误5：为满足注释规则扩大高风险重构

**错误示例：**
```java
// 为了满足注释规则，将整个方法拆分成多个小方法
public void processOrder(String orderId) {
    validateOrder(orderId);
    checkInventory(orderId);
    calculatePrice(orderId);
    createPayment(orderId);
    sendNotification(orderId);
}

// 拆分后的方法，每个方法都需要注释，但增加了维护成本
private void validateOrder(String orderId) { ... }
private void checkInventory(String orderId) { ... }
private void calculatePrice(String orderId) { ... }
private void createPayment(String orderId) { ... }
private void sendNotification(String orderId) { ... }
```

**正确示例：**
```java
// 保持原方法不变，但在关键逻辑段落添加业务注释
public void processOrder(String orderId) {
    // 【订单校验】验证订单状态和数据完整性
    // 业务目的：防止处理无效或异常订单
    Order order = orderMapper.selectById(orderId);
    if (order == null || !order.getStatus().equals("PENDING")) {
        throw new BusinessException("订单状态异常");
    }
    
    // 【库存检查】检查商品库存是否充足
    // 业务目的：防止超卖
    // 数据来源：inventory 表，根据商品ID查询
    Inventory inventory = inventoryMapper.selectByProductId(order.getProductId());
    if (inventory.getQuantity() < order.getQuantity()) {
        throw new BusinessException("库存不足");
    }
    
    // ... 其他逻辑段落
}
```

## 历史代码处理

### 核心原则

- **不要求为补注释而拆分超长历史方法**：不为了满足注释规则而强制拆分超长的历史方法，因为拆分可能会带来业务风险、改变事务边界或扩大测试范围
- **但仍必须添加业务注释**：在不改变方法结构的前提下，为历史方法的关键业务逻辑段落添加注释
- 原位修复时补齐当前方法业务段落
- 新增独立业务能力时再按分层规范落入 Service
- 旧注释与现有代码不一致时必须更新或删除

### 正确理解

**不要求拆分** ≠ **不需要注释**

| 场景 | 正确做法 |
|------|----------|
| 历史方法很长（如 200+ 行） | 保持方法结构不变，在关键业务逻辑段落添加注释 |
| 历史方法有复杂的业务逻辑 | 为每个逻辑段落添加注释，解释"为什么存在、数据从哪来、处理后到哪里去" |
| 历史方法直接调 Mapper | 不因为分层问题而重构，但在 Mapper 调用处添加业务注释 |
| 历史方法有 Controller 业务逻辑 | 不因为分层问题而迁移，但在业务逻辑处添加注释 |

### 反面案例

**错误理解：**
```java
// 因为是历史方法，所以不需要添加注释
public void processHistoricalOrder(String orderId) {
    // 200 行代码，没有任何注释
    Order order = orderMapper.selectById(orderId);
    // ... 复杂的业务逻辑 ...
}
```

**正确理解：**
```java
// 历史方法保持结构不变，但为关键业务逻辑段落添加注释
public void processHistoricalOrder(String orderId) {
    // 【订单查询】根据订单ID查询订单信息
    // 数据来源：order 表
    // 业务目的：获取订单当前状态，用于后续业务处理
    Order order = orderMapper.selectById(orderId);
    
    // 【订单状态校验】验证订单是否可以处理
    // 业务目的：防止处理无效或异常订单
    // 分支场景：订单不存在或状态异常时抛出异常
    if (order == null || !order.getStatus().equals("PENDING")) {
        throw new BusinessException("订单状态异常");
    }
    
    // ... 其他业务逻辑段落 ...
}
```

## 建立检查机制

### 编辑前检查（必须执行）

**每次 Edit/Write 修改业务代码时，必须先输出检查清单**：

```
【X档 · 编辑前检查】
- [ ] 已读取目标代码，理解业务上下文
- [ ] 已确认修改范围，不扩大影响
- [ ] 已确认版本控制纪律
- [ ] 涉及业务注释时，按 annotation.md 标准审查
- [ ] 涉及前端 **.vue、**.html、**.js、**.css 文件修改时，按 frontend.md 标准审查
→ 全部基于事实勾选后方可编辑
```

**检查要点：**
- 是否真正理解了代码的业务上下文？
- 是否知道为什么要修改这段代码？
- 修改会影响哪些其他逻辑？
- 是否需要添加或更新业务注释？

### 编辑时检查（必须执行）

**修改代码时，必须按照注释内容维度覆盖**：

1. **业务目的**：这段代码解决什么需求或防止什么业务错误？
2. **数据流转**：数据从哪来，经过什么转换，写到哪里或返回给谁？
3. **外部交互**：调用什么系统，目的、数据格式和失败策略是什么？
4. **持久层调用**：查询/写入什么数据，条件含义、返回值和后续用途是什么？
5. **分支场景**：什么业务场景进入该路径，结果有什么差异？
6. **风险约束**：为什么要保留顺序、去重、恢复字段、隐藏金额或避免 N+1？

**数据库调用必须说明6个要素：**
1. 数据来源：业务实体或表名、关键字段
2. 业务目的：为什么需要这次查询
3. 条件含义：ID、状态、组织、项目编码等条件代表什么
4. 结果用途：查询结果用于哪个 Map、分支、响应字段或后续调用
5. 空结果处理：跳过、返回空、报错还是降级
6. 性能意图：处于循环相关逻辑时，说明批量查询如何替代逐条访问

### 编辑后复查（必须执行）

**修改完成后，必须执行复查（DoD）**：

```
【编辑后复查】
- [ ] 方法全覆盖：所有适用逻辑段落均已审查
- [ ] 查询用途：每个数据库调用都有来源、目的、条件、结果去向
- [ ] 分支语义：关键分支说明业务场景和影响
- [ ] 一致性：注释与当前代码完全一致
- [ ] 变更范围：未为注释或分层扩大历史代码重构
- [ ] 代码实查：必须确认注释已写入文件，禁止在交付总结中声称已添加但实际未写入
→ 全部通过后，代码任务才算完成
```

**复查要点：**
- 注释是否解释了"为什么存在、数据从哪来、处理后到哪里去"？
- 注释是否与代码行为完全一致？
- 是否有遗漏的逻辑段落没有添加注释？
- 是否有错误的注释需要修正？

## 禁止行为总结

| 错误类型 | 错误示例 | 正确做法 |
|----------|----------|----------|
| 仅描述代码动作 | `// 查询用户` | 解释为什么需要查询用户 |
| 只注释修改行 | 忽略同方法其他段落 | 审查全方法业务逻辑段落 |
| 一条宽泛注释覆盖多个查询 | `// 处理用户信息` | 每个查询和分支单独注释 |
| 注释与代码行为不一致 | 注释说检查权限，代码检查状态 | 确保注释与代码完全一致 |
| 为满足注释规则扩大重构 | 拆分超长方法 | 保持原结构，在关键段落添加注释 |

仅当全部通过，代码任务才算完成。
