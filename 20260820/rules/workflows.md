# 开发工作流

> 决策优先级见 CLAUDE.md §二。
> 工程规范见 engineering-core.md；设计模式见 design-principles.md；注释标准见 annotation.md；陷阱见 pitfalls.md。

## 核心原则

- 一次只解决已确认的问题
- 历史代码默认最小修复，不顺手做架构重构
- 新增代码优先采用设计模式和组件化
- 修改方法后必须执行全方法业务注释复查
- **每次代码编辑后必须执行影响面审查**，确认修改不波及无关功能
- 无验证证据时不得声明完成
- 短信、企业微信、邮件和推送等外部通知变更，默认使用样例断言、mock/stub 或隔离测试接收端验证内容、接收路由和缺失字段分支；未经本次任务明确授权，不得向真实接收人发送测试消息。
- **设计前 HARD-GATE**：只要实施仍依赖未明确的业务语义、权限差异、金额口径、状态流转、审批/工作流、事务边界、跨模块接口或存在多种会改变行为的技术方案，无论改动看起来多小，都必须先探索事实、指出缺失决策、比较可行方案并等待用户批准。用户仅点名文件、字段、方法或期望结果，不等于已经决定上述业务规则。只有用户已逐项明确行为与范围，且代码、数据和现有规则中不存在仍待取舍的业务假设时，才不重复索取方案批准；风险判定、路径核验、注释审查和验证门槛仍须执行。规则维护另按全局 `CLAUDE.md` R 档执行。

## 操作风险与授权执行

- 按全局 `CLAUDE.md` 判定 L1/L2/L3；风险判定与设计、业务假设及注释门槛相互独立。
- 用户直接且无歧义的实施指令，或对精确方案的批准，构成对应范围的 L2 授权；完成其余适用检查后立即执行，不再以笼统安全条款拒绝或重复索取同一授权。该授权不替代 `business-assumptions.md` 的业务假设确认、全局 `CLAUDE.md` §四的编辑检查或其他独立质量门槛。
- 授权仅覆盖用户点名的操作、文件、字段和本次任务；需求变化、范围扩大或后续任务必须重新授权。
- 工具权限 allowlist 只表示工具可调用，不代表用户已授权具体 L2 操作。
- L3 直接拒绝，不得通过拆分命令、改写工具或要求用户重复确认来规避。

## 流程路由

| 场景 | 详细规范 | 说明 |
|------|---------|------|
| Bug 修复 | 本文件核心原则 + engineering-core.md | 复现 -> 追踪 -> 诊断 -> 修复 -> 注释复查 -> 验证 -> 相邻回归 |
| 新增功能 | 本文件核心原则 + business-assumptions.md + design-principles.md | 需求理解 -> 业务规则确认 -> 影响分析 -> 接口设计 -> 实现 -> 注释 -> 测试 |
| 设计前流程 | 本文件 HARD-GATE | 探索 -> 澄清 -> 方案比较 -> 呈现设计 -> 用户批准 |
| 代码审查 | 本文件交付要求 + engineering-core.md 完成检查 | 按业务正确性、安全、权限、事务、性能、并发和交互逐项核对 |
| 交付 | `delivery.md` | 标准交付结构模板 |
| 前端性能（页面无响应/卡顿） | `engineering-core.md`「前端性能排查」 | Trace + 网络请求 + 控制台错误 -> 定位瓶颈 -> 验证 |
| 图表与可视化 | `archify` 技能（用户明确要求时） | 先确认数据、受众和输出介质，再设计和验证 |

各场景按本文件与对应 rules 执行；Skill 调用遵循更高优先级运行时指令，用户显式 `/命令` 直接调用。上级要求命中 Skill 时自动调用的，按要求执行；其余场景按本文件的触发条件执行。

## 规则文件维护（R 档执行流程）

全局 `CLAUDE.md` §4.4 是 R 档的最高级门槛，本节只规定执行顺序，不另行放宽或重定义其强制项：

1. **发现**：完整读取目标规则文件，并检索同一概念在顶层规则、专项细则、模板、示例和检查清单中的全部落点。
2. **追溯**：为每项拟修改内容标明来源；用户明确约定和最高级规则优先于历史摘要、旧会话推测或下级重复文本。
3. **比较**：展示精确旧文本、新文本、影响文件和强度分类；发现削弱时停止，不得将其包装成等价精简。
4. **批准**：语义变化取得用户对精确差异和文件范围的批准；纯格式、错别字和失效引用修复按全局规则直接处理。
5. **实施**：由主代理在批准范围内编辑；不得借同步之名扩大到未列明文件或引入新约束。
6. **验证**：扫描旧措辞残留、重复定义、错误引用、Markdown 结构及正文—模板—清单一致性；逐项说明增强能力是否仍可被实际验收。

规则去重必须保留一个明确的权威来源和所有必要的可执行引用。删除下级重复文本前，先确认权威来源已覆盖原有强度、默认值、例外和验收项；否则属于削弱，不得删除。

## 修改后影响面审查（强制）

**每次代码编辑完成后，必须执行一次影响面审查，确认本次修改不会波及无关功能。**

### 触发时机

- Bug 修复的 Edit/Write 完成后
- 新增功能的 Edit/Write 完成后
- 任何涉及共享类、共享注解、共享 Service 的修改后

### 审查内容

1. **共享依赖检查**：修改的类/注解/接口是否被其他模块引用（grep 类名、注解名、方法名）
2. **调用链覆盖**：同一方法是否在其他 Service 中有平行实现（如同名 compare 方法）
3. **注解传播**：修改注解值后，所有使用该注解的代码路径是否都能正确处理新值
4. **数据流完整性**：修改字段映射/转换逻辑后，前端赋值、后端装配、导出、邮件通知等全链路是否一致

### 审查方法

Grep 修改的类名/注解名 -> 逐个确认引用方是否需要同步修改 -> 需要改的立即补充，不需要的记录排除理由。

### 与完整代码审查的关系

轻量自查（每次 Edit 后）聚焦「是否波及无关功能」；交付前完整审查按业务正确性、安全、权限、事务、性能、并发和前端交互逐维度核对。

### 与 `engineering-core.md`「修改后全方法审查」的关系

两者互补，均需执行，聚焦不同：
- **本审查（影响面）**：聚焦跨方法/跨模块，确认修改不波及无关功能。
- **全方法审查**：聚焦方法内，审查被修改方法的全部业务逻辑段落，见 `engineering-core.md`「修改后全方法审查」。

- **多模型交叉审查（可选）**：当修改同时涉及事务、并发、权限、跨模块接口、公共组件，或预期修改不少于 4 个文件时，必须评估是否需要独立交叉审查；若不采用，交付中写明排除理由。交叉审查结果只能作为主代理复核材料，不替代主代理判断。

## 多端业务一致性对齐（强制）

**触发条件**：用户要求将 A 端（如 PC）的功能在 B 端（如移动端/小程序）复刻或对齐时。

**禁止行为**：
- 仅比对数据模型字段（DTO/Entity）就宣称一致；数据模型中有字段不代表目标端模板中有绑定
- 仅读取源端静态代码中的 v-model 绑定就断言字段列表；低代码生成页面的标签通过 `label_XXXtext` 变量控制，不在模板标签文本中
- 未对比字段顺序、标签文案、禁用状态、下拉数据源和校验规则就声称对齐
- 假设数据源一致；同名 API 文件可能来自不同模块，接口返回数据域不同（如 `wechatmodule` vs `zygl`）

**必执行的对齐核验步骤**：

1. **源端运行时字段清单**：使用浏览器 DevTools 或 `mcp__chrome-devtools__evaluate_script` 提取源端页面所有可见表单控件的 label、value、disabled 状态；不得仅靠静态代码提取
2. **目标端数据模型覆盖度**：逐字段核对目标端数据模型是否包含源端所有字段；缺失字段必须补齐
3. **模板绑定覆盖度**：逐字段核对目标端模板是否绑定了源端所有可见字段；未绑定字段不得声称对齐
4. **字段顺序与标签**：对比源端与目标端每个 Tab/分区的字段顺序和中文标签；标签必须与源端完全一致（包括括号、"甲方/乙方"等修饰词）
5. **下拉数据源**：对比每个下拉字段的接口 URL、查询参数和响应格式；同名字段可能来自不同数据域
6. **禁用/只读状态**：对比每个字段在源端的 disabled/readonly 状态；如银行字段在源端为自动回填禁用，目标端不得开放编辑
7. **运行时验证**：对齐完成后，在目标端浏览器中逐 Tab 截图，与源端截图逐字段比对；不得仅凭代码审查宣称完成

**验证标准**：目标端运行时页面的字段集、顺序、标签、数据源、禁用状态与源端完全一致，无遗漏、无多余、无标签偏差。

## 历史代码修改

允许原位修复的场景及处理要求见 `engineering-core.md`「渐进式架构治理」。核心：保持业务结果、控制最小范围、补齐注释、不因分层问题扩大重构。

## 交付要求

代码变更的交付内容、简化模板、测试数量披露、业务注释实查和风险分级以 `delivery.md` 为唯一权威来源；本文件不另行维护缩减版清单，避免正文与验收项漂移。
