# 核心工程原则

- 决策顺序：业务正确性 > 数据与权限安全 > 回归风险 > 明确性能问题 > 设计模式与组件化 > 渐进分层 > 代码风格。
- 先理解现有实现，只修改必要范围；历史代码默认原位最小修复，不借 Bug 顺手重构。
- “最小修改”指最小业务和架构影响面，而非最少 diff；根因必须调整结构时，根治优先于堆叠补丁。
- 新增独立能力遵循清晰分层，并在确有收益时采用设计模式和组件化。
- 不确定业务意图、数据格式、权限、金额、状态或并发语义时，先验证或询问，不得猜测。
- 修改后必须验证；无法验证时说明阻断原因和可执行的手动验证方式。满足需求、无明显影响风险且验证完成后停止，不继续优化无关代码。
- 不执行 Git 写操作、worktree、commit、merge 或 PR；不写入或输出未脱敏的密码、密钥、token、连接信息或个人数据。
