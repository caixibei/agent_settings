# 业务注释要求（绝对强制）

适用于代码新增、修改、删除和重构。目标是保存难以从语法直接推断的业务知识，降低历史代码维护风险。

**触发时机**：每次 Edit/Write 修改业务代码前自动执行，与代码变更在同一次 Edit 中一起写入。

## 规则职责边界

- 本文件是业务注释内容、Javadoc 格式、逻辑段落覆盖和编辑前 A/B/C 注释审查的主规则。
- `java/engineering.md`、`frontend/vue.md` 和 `routing.md` 可以引用本文件的注释要求，但不改变本文件对注释内容的判定标准。
- 本文件不负责跨模块影响面、事务与性能原则、前端组件规范或最终交付排版；这些事项分别由 `routing.md`、`java/engineering.md`、`frontend/vue.md` 和 `examples/delivery.md` 负责。

## 核心原则

- **能用代码说清楚的，绝不写注释**。写注释前先问：能不能通过重命名、提取方法消除这个注释？
- 注释解释"为什么存在、数据从哪来、处理后到哪里去"，**不翻译代码**。
- 修改方法任意一行，必须审查该方法全部业务逻辑段落。
- 业务正确性优先。历史方法复杂时，不为满足注释或分层要求强制拆分。
- 无法确认业务意图时标记 `// TODO: [待确认业务意图]` 并提示用户，不得猜测。
- 清单必须基于已读取代码，**禁止先勾选后补审查**。

编辑前检查清单的强制输出格式见 CLAUDE.md §4.3，分档详细清单（A/B/C 档）见本文件末尾「编辑前审查清单（A/B/C 档）」。编辑时审查流程、编辑后复查（DoD）见 CLAUDE.md §四。

## Javadoc 格式规范（可读性）

遵循 Java 官方 Javadoc 规范 + Spring 风格，方法级注释必须使用 `/** */` 格式。

### 核心理念：Why > What > How

先解释"为什么这么做"（设计意图、权衡），再描述"这是什么"，最后才是"怎么实现"。实现细节应尽可能让代码自解释。

### 注释金字塔（按层级侧重）

| 层级 | 注释重点 | 说明 |
|------|---------|------|
| 公开接口 | API 契约 | 前置条件、后置条件、异常、线程安全性 |
| 实现类 | 设计选择 | 用了什么策略/数据结构？为什么这样选？ |
| 私有复杂逻辑 | 业务规则 | 无法重构得更清晰时，解释"为什么"优先于"做了什么" |

### HTML 标签选择规则

**决策流程**：先判断内容类型，再选择对应标签。

| 内容类型 | 应选标签 | 说明 |
|----------|---------|------|
| 单句描述、连续叙述 | `<p>` | 2 项以内且构成完整句子时，内联用逗号/顿号连接即可 |
| **3 项以上枚举** | **`<ul>/<li>`** | **步骤、规则、子功能列表——必须用列表，禁止硬塞进 `<p>`** |
| 有序步骤、优先级排序 | `<ol>/<li>` | 有明确先后顺序的流程 |
| 表名、字段名、方法名 | `{@code}` | 与正文视觉区分，不依赖引号 |
| 引用其他类/方法 | `{@link}` | Javadoc 工具可生成超链接 |
| **关键术语强调** | **`<b>`** | **业务概念首次出现时加粗，与 `{@code}` 区分——`{@code}` 用于代码标识符，`<b>` 用于自然语言术语** |
| 正文内强调 | `<strong>` | 与 `<b>` 等效，用于段落内强调 |

**关键决策规则**：

```
内容是代码标识符（表名/字段名/方法名）？ -> {@code}
内容是枚举列表（≥3 项）？               -> <ul>/<li>
内容是有序流程？                         -> <ol>/<li>
内容是自然语言关键术语？                 -> <b>
以上都不是？                             -> <p> 段落内联
```

### 结构模板

#### 类级 Javadoc

```java
/**
 * 类的业务职责一句话概括（以句号结尾）。
 *
 * <p>涵盖以下能力：
 * <ul>
 *   <li>能力一：简要说明</li>
 *   <li>能力二：简要说明</li>
 *   <li>能力三：简要说明</li>
 * </ul>
 *
 * <p>关键约束或设计说明。
 */
```

#### 方法级 Javadoc

```java
/**
 * 摘要句：一句话说明方法的业务功能（以句号结尾）。
 *
 * <p>详细描述：补充业务背景、计算逻辑、数据流转等。
 * 可使用 {@code 代码片段} 或 {@link 类名} 等内联标签。
 *
 * <p>数据来源：{@code bp_epiboly_project} -> {@code bp_commission_sheet} -> {@code bp_product}
 * <p>通知对象：role_id = 870728159144976384 的供管部角色用户
 */
```

> **何时用 `<ul>` 替代 `<p>`**：当「详细描述」或「业务规则」中包含 **3 项以上并列内容**时，必须使用 `<ul>/<li>` 列表。
> 2 项以内且构成完整句子时，用 `<p>` 内联即可。

### Javadoc 规则

1. **摘要句**：第一句话是摘要，简洁完整地说明业务功能，以句号结尾。Javadoc 工具会提取到概览中。
2. **段落分隔**：用 `<p>` 标记段落起始，段落间用空行 `*` 分隔。
3. **列表标记**：3 项以上枚举内容使用 `<ul>/<li>`，有序步骤使用 `<ol>/<li>`。
4. **代码标记**：表名、字段名、方法名用 `{@code}` 包裹，与正文区分。
5. **链接引用**：首次出现的类/方法名用 `{@link}` 构建文档网络。
6. **关键术语**：业务概念首次出现时用 `<b>` 加粗强调。
7. **块标签**：API 方法使用 `@param`、`@return`、`@throws`；业务方法可省略。
8. **行内注释**：逻辑段落使用 `//` 注释，格式见下方「行内注释规范」。

### Javadoc 正确示例

#### 示例 1：方法级 - 多维度描述（使用 `<p>` 内联）

```java
/**
 * 定时扫描委外项目表，临期的发送通知。
 *
 * <p>业务目的：在委外项目预计完成日期前5天开始，每日向供管部外包负责人发送企微进度预警，督促及时跟进。
 *
 * <p>计算逻辑：预计完成日期 = 外包日期({@code epibolyDate}) + 第三方产品周期({@code bp_third_party_product.cycle})，
 * 提醒触发条件：预计完成日期 - 5天 <= 今天 <= 预计完成日期 且 进度未完成。
 *
 * <p>数据来源：{@code bp_epiboly_project} -> {@code bp_commission_sheet} -> {@code bp_product} -> {@code bp_third_party_product}
 * <p>通知对象：role_id = 870728159144976384 的供管部角色用户
 */
public void sendNoticeforExpiringOutsourcedProjects() { ... }
```

#### 示例 2：`<ul>` + `<b>` + `{@code}` 组合使用

```java
/**
 * 计算运费。业务规则：
 * <ul>
 *   <li>满<b>99</b>元包邮（含99）</li>
 *   <li>不满99元时，普通地区10元，偏远地区20元</li>
 *   <li>偏远地区定义见 {@link RegionType#REMOTE}</li>
```

## 注释内容维度（至少覆盖两个）

1. **业务目的**：解决什么需求或防止什么业务错误？（常见错误：只写"查询用户"，不写"为什么需要查询用户"）
2. **数据流转**：数据从哪来，经过什么转换，写到哪里或返回给谁？（常见错误：只写"设置用户名"，不写"用户名从哪里来，用到哪里"）
3. **外部交互**：调用什么系统，目的、数据格式和失败策略是什么？（常见错误：只写"调用接口"，不写"调用什么接口，目的是什么"）
4. **持久层调用**：查询/写入什么数据，条件含义、返回值和后续用途是什么？（常见错误：只写"查询数据库"，不写"查询什么数据，条件是什么"）
5. **分支场景**：什么业务场景进入该路径，结果有什么差异？（常见错误：只写"如果条件成立"，不写"什么业务场景进入这个分支"）
6. **风险约束**：为什么要保留顺序、去重、恢复字段、隐藏金额或避免 N+1？（常见错误：只写"排序"，不写"为什么要排序，不排序会有什么问题"）

## 数据库调用注释的 6 个要素

涉及 Mapper、DAO、getById、list、page、select*、MyBatis SQL 时，注释**必须说明**：

1. **数据来源**：业务实体或表名、关键字段
2. **业务目的**：为什么需要这次查询
3. **条件含义**：ID、状态、组织、项目编码等条件代表什么
4. **结果用途**：查询结果用于哪个 Map、分支、响应字段或后续调用
5. **空结果处理**：跳过、返回空、报错还是降级
6. **性能意图**：处于循环相关逻辑时，说明批量查询如何替代逐条访问

## 业务注释分类与规范

文档注释（Javadoc）面向 API 使用者，业务代码注释（`//`）面向未来维护这段代码的人。目标读者不同，规范也不同。

### 1. 业务规则与决策——最重要的注释

记录隐藏在代码背后的业务知识。当代码背后有需求文档、会议决议、线上事故修复记录时，必须用注释关联。

### 2. 魔数与常量解释

```java
// ❌ 魔数无解释
Thread.sleep(3000);

// ✅ 解释业务含义
// 支付回调后，银行流水有 3s 延迟，必须等待再查询
Thread.sleep(3000);
```

### 3. 复杂算法与边界条件

当逻辑有非直觉的处理时，注释解释为什么这样处理。

```java
// 先扣库存再创建订单，防止超卖
// 如果反过来，并发场景下可能出现库存扣减成功但订单创建失败的情况
if (!inventoryService.tryDeduct(sku, quantity)) {
    throw new InsufficientStockException(sku);
}
Order order = orderRepository.save(new Order(...));
```

### 4. 临时代码与 TODO

TODO 必须负责任：写清谁、什么时候、什么条件下需要处理，以及不处理的后果。

```java
// ✅ 负责任的 TODO
// TODO(zhangsan) [2026-09-01前] 短信服务商迁移至阿里云，当前使用的腾讯云通道将在9月底下线
// 详见 JIRA-3456
public void sendSms(String phone, String content) {
    tencentSmsService.send(phone, content);  // 临时保留旧通道
}

// ❌ 不负责任的 TODO
// TODO 以后优化
```

### 5. 异常处理注释

不是每个 catch 都要注释，但吞掉异常或异常转换时必须解释。

```java
try {
    paymentGateway.pay(order);
} catch (TimeoutException e) {
    // 支付超时不代表支付失败，后续通过查询接口确认结果，因此不抛异常
    log.warn("支付超时，将异步确认结果: orderId={}", order.getId(), e);
}
```

## 业务注释检查清单

| 代码类型 | 注释重点 | 示例 |
|----------|---------|------|
| 复杂 if 条件 | 业务含义 | `// 只有待支付且未过期的订单才能取消` |
| 魔法数字/阈值 | 来源与原因 | `// 超时时间=对方超时(5s) + 网络抖动(2s)` |
| 异常捕获 | 处理理由 | `// 非核心功能，失败不影响主流程` |
| 复杂正则 | 匹配规则 | `// 匹配2024年新税号格式：15位数字+2位字母` |
| 状态机转换 | 转换条件 | `// 已完成订单不允许回退到待支付状态` |
| 循环/递归边界 | 终止条件 | `// 最多追溯三级上级代理，防止死循环` |

## 禁止行为（关键示例）

### 错误1：仅描述代码动作

```java
// ❌ 查询用户 / 设置用户名 / 保存用户——仅翻译代码，无业务信息
// ✅ 【用户信息校验】查询用户基本信息，用于验证用户是否存在及权限
//    数据来源：sys_user 表；结果用途：后续判断用户角色和数据权限
User user = userMapper.selectById(userId);
```

### 错误2：注释与代码行为不一致

```java
// ❌ 注释写"检查用户是否有管理员权限"，实际代码检查的是用户是否被禁用
// ✅ 注释必须与代码行为完全一致，否则注释比缺失更危险
```

## 历史代码处理

### 核心原则

- **不要求为补注释而拆分超长历史方法**：拆分可能带来业务风险、改变事务边界或扩大测试范围
- **但仍必须添加业务注释**：在不改变方法结构的前提下，为历史方法的关键业务逻辑段落添加注释
- 原位修复时补齐当前方法业务段落
- 新增独立业务能力时再按分层规范落入 Service
- 旧注释与现有代码不一致时必须更新或删除

**不要求拆分** ≠ **不需要注释**：

| 场景 | 正确做法 |
|------|----------|
| 历史方法很长（如 200+ 行） | 保持方法结构不变，在关键业务逻辑段落添加注释 |
| 历史方法有复杂的业务逻辑 | 为每个逻辑段落添加注释，解释"为什么存在、数据从哪来、处理后到哪里去" |
| 历史方法直接调 Mapper | 不因为分层问题而重构，但在 Mapper 调用处添加业务注释 |
| 历史方法有 Controller 业务逻辑 | 不因为分层问题而迁移，但在业务逻辑处添加注释 |

## 注释反模式

| 反模式 | 示例 | 问题 |
|--------|------|------|
| 注释代码块 | `// 旧实现: if (v1) ...` | 版本控制系统会保留历史，直接删掉 |
| 情绪化注释 | `// 前任写的烂代码，忍着吧` | 负能量且无信息量 |
| 过度注释 | 每行一个 `//` | 信噪比极低，埋没真正有用的信息 |
| 编号引用代码 | `// step1: ..., step2: ...` | 用提取方法和清晰命名替代 |
| **枚举塞 `<p>`** | **5 项功能用顿号连在一行 `<p>` 里** | **超过 2 项必须用 `<ul>/<li>` 列表** |
