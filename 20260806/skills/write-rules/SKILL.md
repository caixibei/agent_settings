# 编写规则文件

规则只保存长期自动加载、且能直接改变工程决策的约束。先决定内容归属，再决定是否创建规则；不要把总纲、操作流程、checklist 和自动化检查堆进同一份 Prompt。

## 先决定内容归属

| 内容特征 | 推荐位置 |
|---|---|
| 所有项目、所有会话的最高优先级原则 | `CLAUDE.md` |
| 可复用多步骤方法、排查剧本、设计流程 | skill |
| 稳定且需要自动加载的约束 | `.claude/rules/` |
| 可机械检查的格式、命名或禁止项 | lint、hook、测试或脚本 |
| 一次性背景、进度或任务决定 | 对话、任务或项目文档 |

混合内容拆开：rule 写“必须满足什么”；skill 或 reference 写“按什么步骤做”。例如，完整 A/B/C 注释审查表属于按需检查参考，不应作为所有 Java 修改都要输出的常驻 rule。

**固定输出格式、表格列数、checkbox 数量和检查步骤**优先归入 checklist/reference；可自动判定时归入 automation。即使已有规则提到相同主题，也不能仅因“已有覆盖”就把这些格式要求升级为长期 rule。只有“业务结果必须满足的条件”才适合保留为 rule。

## 规则元信息

在规则正文开头使用以下短结构，帮助人和 agent 判断何时适用：

```markdown
## 规则元信息
- 优先级：critical / high / normal / reference
- 触发文件：`src/components/**/*.vue` 或“全局”
- 触发场景：修改匹配文件的模板、脚本或样式时
- 所有权：用户级 / 项目级
```

- `critical`：安全、数据一致性或用户明确的不可妥协约束。
- `high`：业务正确性、权限、事务、状态或 API 契约。
- `normal`：稳定工程与领域约定。
- `reference`：案例、解释和建议。

这些字段只用于排序和审查，**不改变 Claude Code 的实际加载优先级**。没有明确触发条件的规则不得标为 `critical` 或 `high`。

## 最小创建闭环

1. **分类**：用一句话说明为什么它应放在 `CLAUDE.md`、skill、rule、自动化或临时文档。
2. **查重**：搜索用户级与项目级既有规则，确认没有重复、冲突或更合适的原文件。
3. **定界**：选择用户级/项目级；局部规则写 `paths:` glob，并说明为什么不应全局注入。
4. **编写**：写 3–7 条可直接指导选择的约束，使用明确动词和必要条件。
5. **验证**：检查归属、引用、glob、重复与可执行性。
6. **停止**：说明文件、触发范围和验证方式后结束；不要继续追加教程、案例或流程。

## 风险升级

仅在规则涉及安全、敏感数据、权限、金额、状态机、事务、并发、API 契约或跨模块行为时，先确认业务语义和影响范围。

普通文案、示例、路径说明或明确的局部约束调整，不要求完整设计或用户审批；仍须先读取目标文件并检查重复。

## 停止条件

归属、所有权、触发范围、查重结果、约束和验证方式均明确后即可结束。超过 50 行时，检查是否应拆分独立主题或把流程迁入 skill/reference；不得为了压行数删除必要约束。

## 常见误用

| 误用 | 正确做法 |
|---|---|
| 把“先查配置→查表→比对接口”写成 rule | 将完整排查顺序写成 skill；rule 只保留稳定结果约束。 |
| 把 20 项 checklist 写成每次都输出的 rule | 把它作为按需 checklist/reference；只保留会改变决策的约束。 |
| 未查重就新建规则文件 | 先搜索用户级和项目级规则，优先更新最接近的既有文件。 |
| 用无 `paths:` 的规则处理局部目录 | 验证 glob 后使用路径作用域，并说明不全局注入的原因。 |
| 把正文优先级当成运行时加载器优先级 | 只将其用于排序和审查，不宣称能自动提升优先级。 |
| 为普通规则修改启动完整审批流程 | 按风险分流；只有高风险语义变化才升级。 |
