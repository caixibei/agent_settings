# 工程核心规范

> 决策优先级见 CLAUDE.md §二，不在本文件重复。
> 设计模式与组件化决策见 design-principles.md。
> 历史代码修改流程见 workflows.md。

## 安全编码

- SQL注入：禁止拼接用户输入，使用 MyBatis `#{}` 或参数化查询
- 输入校验：在系统边界校验长度、类型、范围和白名单
- 权限校验：删除、状态、金额和权限变更前验证当前用户权限
- 敏感信息：密码、密钥、token、连接串不得硬编码或写日志
- 文件上传：校验MIME、扩展名和大小，存入非Web直访路径
- 输出安全：用户可控内容进入HTML前防XSS

## 持久层与事务

- 新增事务只放Service；历史位置不因本次局部修复强制迁移
- 事务边界与完整业务操作一致，避免半成功状态
- checked exception需要回滚时显式指定 `rollbackFor = Exception.class`
- 避免在事务内发邮件、调第三方API或执行长耗时操作
- 批量操作评估SQL长度、分批策略、索引和一致性
- 生成`IN`前短路，禁止空集合进入MyBatis `<foreach>`
- **BPM/工作流同库参与 Spring 事务**：Activiti/Flowable 表与业务表同库且共用 DataSource（`SpringProcessEngineConfiguration` 配置正确）时，`completeTask` 操作 `bpm_act_ru_*` 表参与 Spring 事务，事务回滚时工作流推进也回滚。这是避免"工作流已推进但 DB 状态未更新"一致性缺口的关键机制，但事务内不应包含长耗时操作。需先验证配置前提，非所有部署都满足

## 查询与性能

- 循环内出现getById/list/selectOne/远程调用时，先判断N+1
- 可批量时先收集主键或业务键，一次查询并按ID转Map
- 批量查询必须返回用于结果归属的主键
- 全量处理后内存分页属于明确风险；能安全修改时改为数据库分页
- 性能优化不得改变权限范围、过滤规则、排序口径和总数含义
- 性能问题按“后端接口调用链 → SQL 数量与 N+1 → EXPLAIN/索引有效性 → 分页与批量装配 → 前端 DOM 渲染与接口等待”排查；未量化后端瓶颈前，不得以 UI 优化替代服务端诊断。
- 列表查询变慢时，先统计主查询、count、嵌套映射和循环调用实际产生的 SQL；分页结果逐行加载关联数据时，优先收集当前页主键批量查询，并按归属键分组回填。
- 索引优化必须以实际 SQL 的 `EXPLAIN`/`EXPLAIN ANALYZE` 与 `SHOW INDEX` 验证：确认 WHERE、JOIN、ORDER BY 的字段顺序能够命中索引；索引存在但未命中、回表代价高或出现 filesort 时，不得宣称优化完成。
- 后端瓶颈量化完成后，再区分前端 DOM/表格渲染成本、无依赖请求并行度与异步展示策略；接口等待不能直接认定为渲染卡顿。

## 渐进式架构治理

目标结构：请求 → Controller → Service → Mapper/DAO → DB

**新增代码**：严格遵循分层，跨模块新增调用优先走目标模块Service。优先采用设计模式（策略/工厂/模板方法等）降低复杂度，参见 design-principles.md。

**历史代码**：
- Controller已承载业务逻辑时，允许原位最小修复
- 不因历史分层问题强制重构
- 原位修复必须补足业务注释

## 导出数据不一致排查

先从前端导出按钮追踪实际请求 URL，再定位对应 Controller、Service 和 Mapper；逐项对比列表查询与导出路径的筛选条件、字段映射、权限范围和空结果处理。

## 并发优化与多线程

后端性能优化遇到**多个相互独立的操作**时（如多个无依赖的查询、批量装配中的辅助表查询、无数据依赖的远程调用），应评估并发多线程方案。禁止遇到性能问题只想到加索引和缩事务。

### 何时考虑并发

| 场景 | 是否适合并发 | 原因 |
|------|------------|------|
| 多个无依赖查询（如装配列表时查字典、查用户、查组织） | ✅ 适合 | 各查询无数据依赖，可并行缩短总耗时 |
| 批量操作中的独立子任务 | ✅ 适合 | 各子任务无共享状态 |
| 有数据依赖的操作（先查后写、先读后判断） | ❌ 不适合 | 后一步依赖前一步结果，强行并发引入竞态 |
| 操作同一数据行 | ❌ 不适合 | 并发争用行锁，不如串行 + 锁机制 |
| 事务内的操作 | ⚠️ 谨慎 | 并发可能改变事务边界和锁持有时间 |

### 框架选型

- **技术栈含 Guava 时优先使用**：`ListeningExecutorService` + `Futures`/`ListenableFuture` 提供回调式异步编排，比裸 `Future.get()` 阻塞更优
- **无 Guava 时**：JDK `CompletableFuture` 或 `ExecutorService`
- **禁止**为单次优化引入新框架依赖；优先复用项目已有线程池配置

### 数据一致性优先原则（强制）

**性能优化不得以牺牲数据一致性为代价。** 并发引入后必须重新评估：

1. **乐观锁/悲观锁选型**：并发后冲突概率升高，必须按下方「并发控制机制选型」决策矩阵重新评估
2. **事务边界**：并发操作是否在同一事务内？跨线程操作同一事务会导致 Spring AOP 事务失效
3. **结果聚合的原子性**：多个并发查询结果汇总时，部分失败如何处理？是否需要降级
4. **禁止**「为保性能跳过一致性校验」--如果业务规则要求 check-then-act，必须用锁定读（FOR UPDATE）或 CAS，不能用并发绕过校验

## 并发控制机制选型

修改涉及 check-then-act（先读后写）模式时，**必须先评估并发控制机制**，禁止直接用最熟悉的方案。

### 决策矩阵

| 条件 | 推荐方案 | 理由 |
|------|---------|------|
| 单 MySQL 实例 + 低冲突 + 高操作代价 | **MySQL FOR UPDATE**（悲观锁） | 无额外依赖，锁与事务天然绑定，避免无谓重试 |
| 单 MySQL 实例 + 高冲突 + 低操作代价 | **CAS 乐观锁**（version 字段或状态条件更新） | 不阻塞读，并发冲突快速失败 |
| 跨服务 / 跨库 / 微服务架构 | **Redis 分布式锁**（Redisson） | 跨进程协调，需要续期和崩溃恢复机制 |
| RR 隔离级别 + 需要读最新数据 | **必须用锁定读**（SELECT ... FOR UPDATE） | MVCC 快照读无法读到其他事务已提交的值 |

### 评估维度（必须逐项回答）

1. **冲突概率**：同一数据行被并发操作的可能性有多高？
2. **操作代价**：冲突时重试的成本有多大（秒级 vs 毫秒级）？
3. **一致性要求**：业务不变量被违反的后果有多严重？
4. **架构约束**：当前是单体还是分布式？是否有跨库需求？
5. **改造成本**：引入新机制需要改多少代码？是否需要新依赖？

### InnoDB 行锁核心规则

InnoDB 行锁**加在索引记录上**，不是数据行上。任何 DML（SELECT FOR UPDATE / DELETE / UPDATE）的 WHERE 条件**没有可用索引** → RR 隔离级别下锁全表。加索引是消除全表锁的第一优先级。

### 性能问题技术评审流程（强制）

涉及并发控制 / 锁机制选型的性能优化，**必须完成以下技术评审**，禁止直接动手改：

1. **画并发时序图**：列出所有并发操作同一数据的请求路径（包括独立 HTTP 请求），标注锁冲突点
2. **EXPLAIN 验证**：对所有涉及锁的 SQL 执行 EXPLAIN，记录 type、rows、key 列
3. **SHOW INDEX 验证**：确认 WHERE 条件字段是否有索引
4. **量化锁持有时间**：事务内所有操作的预估耗时（查询次数 × 单次耗时）
5. **方案对比矩阵**：列出 ≥2 个方案，从改造成本、风险、性能提升、适用场景四个维度对比
6. **索引优先原则**：优化顺序——加索引（消除全表锁） > 缩事务（减少持锁时间） > 换锁机制

**禁止行为**：
- ❌ 不做 EXPLAIN 就加索引（可能索引不生效）
- ❌ 不画时序图就选乐观锁（可能遗漏并发场景）
- ❌ 只优化单个触点，不审查完整调用链

### 并发防护验证清单（强制）

锁机制选型后、动手实施前，必须逐项验证，禁止假设防护已生效：

1. **自定义事务注解的实际行为**：项目自定义事务注解（如 `@HussarTransactional`）不能假设等于 Spring 标准 `@Transactional`。必须反编译或查拦截器实现，确认隔离级别（RR/RC）、传播行为、回滚规则（是否对 Exception 回滚）。悲观锁依赖事务生效，乐观锁在 RR 下有 check-then-act 陷阱，判断都依赖隔离级别，框架注解可能覆盖默认值。

2. **乐观锁三件套验证**：实体有 version 字段**不等于**有乐观锁。三件套必须齐全，缺一不生效：
   - 字段标注 `@Version`（MyBatis-Plus 乐观锁注解），不是 `@TableField("VERSION")`
   - 配置 `OptimisticLockerInnerInterceptor` 拦截器
   - 历史数据 version 有值（NULL 时 MyBatis-Plus 跳过乐观锁条件，退化成普通 update）

3. **锁范围覆盖所有写库点**：悲观锁/CAS 守护一个写点不够。必须审查完整调用链上**所有** `saveOrUpdate`/`update` 点，确认每个点要么受锁保护、要么用最新对象（非旧状态）。漏一个写点就覆盖回旧值。重点排查"中间人"方法（如 `flowFormSubmit` 内的冗余 `saveOrUpdate`），它带着旧状态对象在锁释放后写库，是并发覆盖的隐蔽元凶。

4. **事务方法调用方式**：`@HussarTransactional`/`@Transactional` 方法必须通过代理调用（跨类注入、`AopContext.currentProxy()`），不能同类 `this.xxx()`。但 `this` 调用**无注解**的基础方法（如 MyBatis-Plus `saveOrUpdate`）不影响事务--失效仅发生在 `this` 调用另一个**带注解**的事务方法时。

## 公共 Java API 契约

修改公共 Java 类的新增、重载、覆写或兼容方法时，按 `annotation.md`「公共 API 与兼容入口注释」审查完整公开方法集合。重载或覆写方法的 Javadoc 必须说明与同名方法或父类契约的差异、适用业务场景及最小调用示例；兼容入口必须用 `@Deprecated` 标明替代方法、保留原因和迁移方式。

## 修改后全方法审查

修改方法后，审查该方法全部业务逻辑段落，确认注释、分支、数据库调用、空结果处理和异常语义与代码一致。

## 需要用户确认的情况

- 拆分超长核心方法
- 改变事务边界
- 将Controller逻辑迁移到Service
- 跨模块改接口
- 修改工作流、权限或金额计算

## 前端性能排查：浏览器「此页面无响应」

用户报告页面无响应、卡顿或 loading 很久时，先采集浏览器性能 Trace、网络请求和控制台错误，再根据数据定位瓶颈；不得仅凭静态代码猜测。


## 完成检查

### 后端

- 业务结果和边界场景符合预期
- 权限、状态、金额和敏感数据未受损
- 查询无明显新增N+1
- 变更涉及查询方法时，已同步检查对应导出方法的筛选条件和字段映射
- 多文件编辑后，已审查每个修改文件的 import/require 语句，确认路径存在且引用正确
- 历史分层问题未导致无关重构
- 业务注释符合annotation.md
- 已执行可用验证，或明确说明环境阻断
- 涉及 check-then-act 模式时，已评估并发控制机制（悲观锁 / 乐观锁 / Redis 锁）并说明选择理由
- DML 的 WHERE 条件已确认有索引，无全表锁风险
- 有数据依赖的异步操作已 await，无并发争锁风险

### 前端布局

- 查询条件在最小适用宽度（1280px）下全部可见，无字段被挤出视口
- 表格高度随查询区换行自动调整，不会被挤出视口底部
- 空间不足时内容换行而非溢出隐藏（禁用 `overflow: hidden` 隐藏业务内容）
- 布局修改优先调整容器结构，其次流式布局，最后 CSS 计算
- 已在浏览器验证或说明环境阻断原因
